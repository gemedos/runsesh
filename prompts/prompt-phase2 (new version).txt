STEP B3: THE INGESTION FUNCTION (supabase/functions/ingest-steps/index.ts)
The source lives in the repo; I deploy it by pasting it into the dashboard editor. Pin every imported package to an exact version and verify it exists. Use Web Crypto for hashing and constant-time comparison.
- Accept POST only (405 otherwise). No CORS headers at all. Require Content-Type application/json. Body limit 16 KB (413). Reject everything else with a generic message.
- Read the token from the Authorization: Bearer header (or the method I approve in B1). Split it, look up the token row by id, reject if missing or revoked, and compare SHA-256(secret) with secret_hash in constant time. Every authentication failure returns the same 401 response body, whatever the reason.
- Rate limit per token, for example 20 requests per hour (the apps sync at most every 15 minutes); return 429 when exceeded. Update last_used_at on success.
- Parse the payload with two adapters: (1) the GENERIC format {"day":"YYYY-MM-DD","steps":12345} or {"days":[{"day":"...","steps":...}]}, which the later iPhone Shortcut phase will use; (2) the chosen app's real format from B1. Convert timestamps to the user's local day using profiles.timezone (an IANA name; fall back to UTC if invalid).
- Validate strictly: at most 3 days per request; each day a real calendar date inside the same window as the daily_steps trigger (3 days back to 1 day ahead); steps an integer from 0 to 100000. If any item is invalid, reject the whole request (400) and write nothing.
- Write with an upsert into daily_steps for the token owner only. user_id comes from the token row, NEVER from the payload. Source is 'health_connect' for android tokens and 'shortcut' for ios tokens. Use the function's built-in privileged environment only inside the function; nothing privileged leaves it.
- Response: {"ok":true} on success. Never echo input, error details, stack traces or system information.
- Logging: only the token id and an outcome code. Never log payloads, secrets, emails or step values.
